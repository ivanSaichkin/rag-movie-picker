# Python RAG сервис

Локальная реализация поиска фильмов: собственный BM25, трансформерные эмбеддинги, Qdrant, RRF и LLM через OpenRouter-совместимый API. Go-бэкенд и подключение фронтенда не входят в этот сервис.

Отдельная [документация по архитектуре RAG](docs/architecture.md): компоненты, хранение данных, алгоритмы и прохождение запроса.

## Установка

Нужны Python 3.12 или 3.13 и uv. Все команды ниже выполняются из каталога `recommender`. Параметры хранятся в `config.toml`; Python-модели в `config.py` только валидируют файл. Неизвестные ключи отклоняются. Пути к CSV, состоянию и embedded Qdrant разрешаются относительно выбранного TOML-файла.

```powershell
uv sync --locked --extra embeddings
```

Для генерации задайте `llm.model` в TOML и ключ в локальном `.env` рядом с конфигом:

```dotenv
LLM_API_KEY=ваш_ключ_OpenRouter
```

В `config.toml` выбран платный [DeepSeek V4 Flash 0731](https://openrouter.ai/deepseek/deepseek-v4-flash-0731). `llm.reasoning_enabled=false` отключает рассуждения; `llm.structured_outputs=true` включает строгую JSON-схему для отбора и, если включён перевод, отдельную схему перевода. OpenRouter получает `provider.require_parameters=true`, чтобы не отправлять запрос провайдеру, который игнорирует эти настройки. Схемы строятся из тех же Pydantic-моделей, которыми сервис проверяет ответ; ID, дубликаты и лимит дополнительно проверяются локально. Схема не гарантирует фактическую точность пояснения. Фактическую стоимость смотрите в `usage` диагностического ответа: она зависит от провайдера, токенов и кэша. Смена LLM требует перезапуска сервера, но не пересборки индекса.

Если поля не заданы, прежние конфиги сохраняют поведение: JSON mode и рассуждения по умолчанию провайдера. Для режима без строгой схемы задайте `structured_outputs=false`; чтобы вернуть настройки рассуждений провайдера, удалите `reasoning_enabled` из TOML.

Флаг `disable_llm=true` выключает все вызовы LLM. В русском индексе BM25 и hybrid работают с исходным запросом без перевода и без переключения стратегии. Флаг `generate_explanations` по-прежнему управляет только финальным отбором.

Шаблон — `.env.example`. Если `.env` ещё нет, скопируйте шаблон; существующий файл с ключом не перезаписывайте. Для работы с LLM нужны `llm.enabled=true`, `llm.model` и ключ; для финальных объяснений — `search.generate_explanations=true` или флаг запроса. В тетрадке включите «Выбор и объяснения LLM». После изменения ключа перезапустите RAG. Изменение CSV, токенизатора или эмбеддера требует нового индекса.

Переменная окружения процесса имеет приоритет над `.env`, включая явно пустое значение:

```powershell
$env:LLM_API_KEY = "ваш_ключ"
```

`qdrant.path = ".qdrant"` включает embedded Qdrant без Docker; иначе используется `qdrant.url`. Embedded-режим поддерживает поиск и фильтры, но не ускоряющие payload-индексы. При запуске `serve` ключ читается из `.env` рядом с выбранным TOML или из файла `--env-file путь`. Из него используется только переменная, названная `llm.api_key_env`; остальные параметры остаются в TOML. Прежние переменные настроек вроде `RETRIEVAL_STRATEGY` не используются. `.env` исключён из Git, шаблон `.env.example` можно коммитить.

Трансформер работает локально на CPU, первая загрузка требует интернета и места для весов. Модель и revision зафиксированы в TOML. `transformer.local_only = true` запрещает скачивание. Если в индексе только BM25, трансформер не загружается; достаточно `uv sync --locked` без extra `embeddings`.

## Состав индекса и стратегия поиска

| `index.enabled_vectors` | Доступные стратегии запроса |
| --- | --- |
| `["bm25"]` | `bm25` |
| `["transformer"]` | `transformer` |
| `["bm25", "transformer"]` | `bm25`, `transformer`, `hybrid` |

`search.default_strategy` выбирает поиск по умолчанию; запрос может переопределить его полем `strategy`. Запрос отсутствующего представления возвращает `INVALID_ARGUMENT`, а несовместимая стратегия по умолчанию отклоняется при загрузке конфигурации. В Qdrant создаются только выбранные именованные векторы: `bm25` и/или `semantic`.

Для полностью автономного BM25 есть готовый `config.bm25.toml`: только разреженный индекс, embedded Qdrant, русский и английский стемминг, без LLM и трансформера:

```powershell
uv sync --locked
uv run --locked python scripts/prepare_russian_dataset.py
uv run --locked movie-rag import --config config.bm25.toml
uv run --locked movie-rag serve --config config.bm25.toml
```

В другом терминале:

```powershell
uv run --locked python scripts/query.py "space adventure" --strategy bm25 --limit 10 --no-generate-explanations
```

Для transformer-only установите `index.enabled_vectors = ["transformer"]` и `search.default_strategy = "transformer"`. Для hybrid оставьте оба представления. Примеры конфигурации используют разные каталоги состояния и коллекции, чтобы не перезаписывать индекс.

## Импорт и запуск

```powershell
uv run --locked python scripts/prepare_russian_dataset.py
uv run --locked --extra embeddings movie-rag import
uv run --locked --extra embeddings movie-rag serve
```

Импорт читает CSV, строит только выбранные представления и сохраняет manifest в `index.state_dir`. LLM при импорте не вызывается. Сервер слушает `server.address`, по умолчанию `127.0.0.1:50051`. Остановка — Ctrl+C. Для своего TOML используйте `--config путь/к/config.toml` после `import` или `serve`.

Существующие коллекции не удаляются. Повторный импорт неизменившегося датасета проверяет индекс без дублирования. Изменение состава векторов, CSV или параметров активного эмбеддера требует **новых** `qdrant.collection` и `index.state_dir`. Смена стратегии поиска, генерации и настроек отключённого эмбеддера не требует пересборки.

Формат manifest обновлён до версии 2. Старые manifest несовместимы: создайте новый индекс, сохранив прежний. Имена стратегий в API теперь `bm25` / `transformer` / `hybrid`; прежние `sparse` / `dense` не принимаются. Имена векторов Qdrant не изменились.

Импорт и сервер одного индекса используют общий файловый lock: перед импортом сервер нужно остановить. Это локальный одноэкземплярный MVP, не распределённая блокировка. При разных директориях состояния на разных хостах блокировка не защищает общую коллекцию.

## Перевод запроса и генерация

По умолчанию используется `tmdb_5000_movies_ru.csv`: скрипт подготовки объединяет исходный CSV с `tmdb_enriched/reports/catalog-4803.json` по ID. Русские название и описание заменяют исходные; при отсутствии перевода остаётся исходный текст. Рейтинги, годы, жанры и ID сохраняются. Рядом создаётся отчёт `.coverage.json`.

`bm25.tokenizer = "snowball-ru-en-v1"` задаёт нижний регистр, `ё → е`, токены `[a-z]+|[а-я]+|[0-9]+` и [Snowball-стемминг](https://snowballstem.org/algorithms/) русского и английского. Документы и запросы обрабатываются одинаково; BM25 и IDF по-прежнему реализованы самостоятельно. Это не лемматизация и не перевод. `query_preparation = "none"` обязателен для этого токенизатора.

Старый `ascii-lower-v1` сохраняется для английских индексов; только в нём режим `query_preparation = "llm"` переводит запрос. Новый русский индекс использует `.state-ru` и `movies_ru_v1`; старый не перезаписывается.

`search.generate_explanations` задаёт финальный выбор и объяснения через LLM по умолчанию. Поле запроса `generate_explanations` переопределяет его. При `false` возвращается поисковый top с `mode=retrieval_only`, без объяснений и без предупреждения о сбое генерации. В русском конфиге перевод не вызывается; в старом английском конфиге он регулируется отдельно.

`llm.enabled = false` запрещает все вызовы LLM, включая перевод и генерацию; флаг запроса не может его включить. Для автономного BM25 задайте также `bm25.query_preparation = "none"`. При включённой, но ненастроенной LLM финальная генерация возвращает fallback с `GENERATION_UNAVAILABLE`.

## Вызов gRPC

Контракт находится в `../proto/rag/v1/rag.proto`; сгенерированные Python- и Go-файлы включены в проект. Запрос можно выполнить встроенным примером:

```powershell
uv run --locked python scripts/query.py "Фантастика про космос" --limit 5
uv run --locked python scripts/query.py "Фантастика про космос" --strategy transformer --limit 10 --no-generate-explanations
```

Доступны `Recommend`, `GetMovie`, `GetCatalog` и стандартный unary gRPC health `Check`. Потоковый health `Watch` не реализован. Порт без TLS предназначен только для localhost/доверенной внутренней сети, не для публичного доступа.

Ответ содержит `mode`, `strategy_used`, `items` и `warnings`. `items` содержат карточки `movie`; общее пояснение передаётся в `explanation`, признак подходящих кандидатов — в `has_matches`. Поле `reason` читается для совместимости со старой историей, новая генерация его не заполняет. `GetCatalog` возвращает также `available_strategies` и `default_strategy`. Неизвестные числовые поля protobuf не устанавливаются. Отсутствующее поле `generate_explanations` отличается от явного `false`. HTTP API и история относятся к Go-бэкенду.

## Слои и зависимости

### Диагностика одного запроса

`RecommendRequest.candidate_limit` задаёт N кандидатов до финального выбора; `limit` — итоговое K. N должно быть от K до `search.max_candidates` (по умолчанию 1000). Если N отсутствует, используется прежняя формула, ограниченная размером каталога и `max_candidates`. Менять состав или перестраивать индекс для этого не нужно. `GetCatalog` сообщает `max_candidates`.

Для исследований есть отдельный RPC `InspectRecommendation` с теми же полями запроса. Он выполняет тот же сценарий, но возвращает `RecommendationInspection`: обычный `response`, `diagnostics` и поля `error_code`, `error_message`. При доменной ошибке можно получить диагностику без успешного `response`; транспортные ошибки и истёкший клиентский дедлайн по-прежнему могут завершать RPC. У обычного `Recommend` сохраняются прежние ошибки gRPC и отсутствие сырых промптов в ответе.

Диагностика содержит пул поиска со score, ID кандидатов, реально отправленных на финальный выбор, время RAG/поиска/вызовов LLM и отдельные HTTP-попытки с телом запроса, ответом провайдера и текстом модели до разбора JSON. Заголовки авторизации не включаются, точное значение API-ключа редактируется. Текстовые поля ограничены 256 Ki символов, обрезание отмечается флагами. Это исследовательский метод для доверенной внутренней сети: в данных есть пользовательский текст и карточки кандидатов; автоматически в журналы они не записываются.

В `research/notebooks/02_recommender.ipynb` добавлен раздел «Полный эксперимент с LLM». После обновления protobuf перезапустите RAG и kernel тетрадки. Выберите golden query, задайте параметры в `EXPERIMENT` и выполните следующие ячейки: кандидаты до/после, метрики относительно golden set, времена и сырые вызовы. Для своего текста несовпадающая разметка автоматически не применяется.

- `models.py`, `ports.py` — модели и интерфейсы.
- `embeddings.py` — BM25, TransformerEmbedder и композиция представлений.
- `preprocessing.py`, `indexing.py` — CSV, форматирование, импорт и manifest.
- `storage.py` — адаптер Qdrant.
- `retrieval.py` — независимые ветки поиска и RRF.
- `llm.py`, `service.py` — адаптер провайдера и сценарий RAG.
- `transport.py` — gRPC и преобразование сообщений.
- `cli.py` — сборка зависимостей и управление ресурсами.

RRF используется только для `hybrid`. Лимит кандидатов: `min(размер каталога, max(search.min_candidates, search.candidate_multiplier × limit))`. LLM не определяет поля карточек: его ID проверяются относительно кандидатов.

Обработчики gRPC синхронные, работают в ограниченном пуле потоков. Модель общая, её вызовы сериализованы. Дедлайн проверяется между этапами и ограничивает сетевые вызовы; уже запущенный inference PyTorch нельзя принудительно прервать, после его завершения просроченный ответ отбрасывается. У клиента gRPC дедлайн срабатывает независимо.

`llm.context_bytes` — бюджет UTF-8 для входа, а не точное число токенов. Его и `llm.max_output_tokens` нужно согласовать с моделью. При невозможности генерации возвращаются поисковые карточки без объяснений; релевантность fallback не гарантирована.

## Проверки

Без тяжёлого эмбеддера:

```powershell
uv sync --locked
uv run --locked ruff check src/movie_rag tests scripts
uv run --locked ruff format --check src/movie_rag tests scripts
uv run --locked pytest
```

Unit-тесты используют fake-эмбеддер и подставной LLM. Интеграционные тесты запускают embedded Qdrant и настоящий gRPC на случайном локальном порту, не требуют Docker, ключа или платных запросов.

Необязательный smoke-test настоящей модели из кеша:

```powershell
uv sync --locked --extra embeddings
$env:RUN_MODEL_TESTS = "1"
uv run --locked --extra embeddings pytest -m model
```

Проверка полного каталога не заменяет оценку качества на размеченных запросах: Precision@k и сравнение стратегий выполняются отдельно.

## Проверки в GitHub Actions

В `.github/workflows` находятся два независимых workflow:

- `rag-ci.yml` — Ruff, тесты на Python 3.12 и 3.13 и сборка пакета. Выполняются unit- и локальные интеграционные тесты с embedded Qdrant и gRPC; тяжёлая модель не устанавливается, тест `model` исключён. Ключ LLM и датасет не нужны.
- `rag-contract.yml` — повторная генерация Python/Go-клиентов, проверка отсутствия изменений относительно коммита, форматирование, `go vet` и Go-тесты с детектором гонок. Версии Go-генераторов совпадают с локальным скриптом.

Проверки запускаются при изменении соответствующих файлов на push в `main`, `development`, `ml_*` и в pull request в `main`/`development`. Также предусмотрен ручной запуск `workflow_dispatch` (интерфейс GitHub требует наличия workflow в default branch). У workflow только права чтения репозитория; они ничего не публикуют и не деплоят.

Это проверки кода и контракта, не проверка качества рекомендаций на полном каталоге или доступности реального LLM API. Из-за фильтров путей workflow может быть пропущен при несвязанных изменениях; учитывайте это при настройке обязательных проверок ветки.

## Точное название и проверка качества

Запрос `Найди фильм «Оппенгеймер»` запускает проверку точного названия по всему индексированному CSV, включая `original_title`, с теми же фильтрами. Отсутствие совпадения возвращает `mode=empty`, `NO_MATCHES` и сообщение. Нормализуются регистр, пунктуация и `ё`; опечатки, транслитерация и произвольные формулировки не распознаются как точный поиск. Запрос «похожие на …» остаётся обычной рекомендацией. Проверка SHA-256 при запуске не позволяет использовать каталог, отличающийся от индекса.

LLM выбирает только из кандидатов и может вернуть пустой список при недостатке данных. Пустой top-N не доказывает отсутствие фильма во всём каталоге. Сбой LLM возвращает отдельное предупреждение и не считается корректным отказом. [Протокол оценки и команды](../evaluation/README.md) описывают 10 обычных запросов, 5 ловушек и метрики.

## Общее пояснение LLM

LLM возвращает JSON следующего вида:

```json
{"movie_ids": [157336, 286217], "explanation": "Начните с «Интерстеллара», если хочется масштабной истории о космосе. Для истории о выживании и изобретательности подойдёт «Марсианин».", "has_matches": true}
```

Это иллюстрация формата, не сохранённый ответ модели. Сервис проверяет ID, уникальность, лимит, непустое пояснение и согласованность признака совпадений. Карточки восстанавливаются из переданных кандидатов. На клиент уходит `items` и одно `explanation`, без новых индивидуальных `reason`.

Если кандидаты не отвечают запросу, LLM ставит `has_matches=false`. Она может вернуть связанные альтернативы, но должна сначала прямо сообщить об отсутствии подходящих вариантов. Сайт дополнительно маркирует такие карточки как альтернативы. Если полезных альтернатив нет — `movie_ids=[]`. Жёсткие фильтры не ослабляются.

При обычном поиске модель оценивает только кандидатов, поэтому не может утверждать отсутствие фильма во всём каталоге. Для строгого запроса `Найди фильм «название»` отсутствие проверяет каталог; LLM получает этот факт и не может переопределить его положительным `has_matches`. При включённой генерации доступны альтернативы, при выключенной возвращается пустая выдача. Найденное точное название возвращается напрямую. Ошибка генерации — `GENERATION_UNAVAILABLE`; она не означает отсутствие совпадений.

Промпт и схема ответа находятся в `src/movie_rag/service.py` (`Selections`, `RagService._generate`). gRPC-поля `explanation` и `has_matches` передаются в Go API, сохраняются в JSONB истории без миграции таблицы и отображаются над карточками. Для применения изменений перезапустите Python и пересоберите Go-контейнер (`docker compose up -d --build` из `backend`). Старые записи истории без этих полей продолжают читаться.

### Контекст и расход токенов

В текущем русском конфиге `bm25.query_preparation="none"`: LLM-перевод отсутствует. При включённой генерации обычно выполняется один вызов отбора; при пустом поиске или выключенной LLM его нет. BM25 и трансформерный эмбеддер работают локально.

Модели передаются системные правила, исходный запрос, фильтры, K, результат проверки точного названия и карточки кандидатов: ID, название, описание, жанры, год, рейтинг и число оценок. Векторы, весь CSV, история пользователя, keywords и original_title в этот вызов не входят.

При K=10 поиск по умолчанию даёт N=30 кандидатов. Общий текст ограничен `llm.context_bytes=24000` байт UTF-8; при превышении хвост списка убирается с `CONTEXT_LIMIT`. Это лимит байтов, не токенов, и он может сократить число реально переданных фильмов.

Два проверочных вызова Gemini 2.5 Flash-Lite 27.11.2026 (не полный бенчмарк качества):

| Запрос | Найдено / передано | Входные токены | Выходные токены | Стоимость API | Время RAG |
| --- | --- | --- | --- | --- | --- |
| Космические экспедиции | 30 / 19 | 4793 | 252 | $0,0005801 | 5,15 с |
| Точное название «Оппенгеймер» | 30 / 21 | 4879 | 60 | $0,0005119 | 0,99 с |

Оба ответа прошли проверку формата; первый вернул подборку, второй — отсутствие точного названия. Это не гарантирует качество ранжирования и каждого утверждения: в первом пояснении модель слишком широко отнесла некоторые фильмы к космическим путешествиям. Для выводов о качестве нужен полный прогон с ручной проверкой. `max_output_tokens=4096` — верхняя граница ответа, а не фиксированный расход. Фактические значения доступны в `usage.prompt_tokens`, `usage.completion_tokens`, `usage.cost` внутри ответа провайдера в диагностике.
