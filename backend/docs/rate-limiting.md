# Ограничение частоты

Документ описывает rate-limiter Go-сервиса: какие ручки ограничены, как считается окно, что происходит при отказе Redis и какие у подхода ограничения. Хранение счётчиков — в [caching.md](caching.md); коды ошибок — в [api.md](api.md).

## 1. Область действия

Лимиты действуют на маршрутах авторизации и гостевого поиска.

| Ручка | Префикс ключа | Окно | По умолчанию | Переменная |
|---|---|---|---|---|
| `POST /api/v1/auth/login` | `login` | минута | 10 | `RATE_LIMIT_AUTH_PER_MINUTE` |
| `POST /api/v1/auth/register` | `register` | час | 20 | `RATE_LIMIT_REGISTER_PER_HOUR` |
| `POST /api/v1/auth/refresh` | `refresh` | минута | 60 | `RATE_LIMIT_REFRESH_PER_MINUTE` |
| `POST /api/v1/guest/recommendations` | `guest` | минута | 10 | `RATE_LIMIT_GUEST_PER_MINUTE` |

Лимит регистрации применяется только при `REGISTRATION_ENABLED=true`. По умолчанию маршрут регистрации отключён.

Значения — целые от 1 до 100000. Остальные ручки, включая каталог и подбор после входа, доступны без лимитера.

## 2. Алгоритм

Фиксированное окно на клиентский IP:

```text
window = 1 минута или 1 час
windowStart = now.Truncate(window)
key = "ratelimit:<prefix>:<client_ip>:<windowStart.Unix()>"
count = cache.Increment(key, ttl=window)
если count > limit:
    Retry-After = секунд до конца окна + 1
    429 RATE_LIMITED
иначе пропустить
```

`Increment` создаёт ключ со счётчиком 1 и ставит TTL только при создании; повторные запросы увеличивают значение и не продлевают окно. Redis делает это атомарным Lua-скриптом (`INCR` + `PEXPIRE` при первом значении), память — под мьютексом.

Окно фиксированное, а не скользящее: на границе минуты/часа счётчик начинается заново. Это просто и предсказуемо, но допускает всплеск до `2 × limit` на стыке окон.

`Retry-After` возвращается только вместе с 429 и указывает на начало следующего окна с запасом в секунду. Заголовков `X-RateLimit-Limit`/`X-RateLimit-Remaining` нет.

## 3. Порядок middleware

Цепочка запроса:

```text
RequestID → Logging → Recovery → CheckOrigin → RateLimit → handler
```

Практические следствия:

- запрос с чужим `Origin` получает 403 до лимитера и не расходует квоту;
- запрос без `Origin` (curl, мобильный клиент) лимитируется как обычно;
- неверный JSON, неизвестные поля и ошибки валидации **расходуют** квоту: лимитер стоит до разбора тела;
- успешный и неуспешный вход считаются одинаково — это защита от перебора, а не только от успешных попыток.

## 4. Хранилище и несколько экземпляров

| Сценарий | Поведение |
|---|---|
| `REDIS_ADDR` задан | Счётчики общие для всех экземпляров, окно согласовано |
| Redis с fallback | При сбое Redis счётчики уходят в память экземпляра; лимиты временно становятся локальными |
| `REDIS_ADDR` пуст | Память процесса; у каждого экземпляра свои счётчики |
| Рестарт процесса с памятью | Счётчики сбрасываются |
| Рестарт Redis в Compose | Счётчики сбрасываются (персистентность отключена) |

При нескольких экземплярах без Redis фактический лимит умножается на их число. Для строгого лимита нужен общий Redis (или внешний прокси/WAF).

## 5. Клиентский IP

Для гостевого поиска используется IP непосредственного TCP-соединения. При размещении за обратным прокси его клиенты разделяют одну квоту.

На маршрутах авторизации ключ строится по `c.ClientIP()` из gin. В gin 1.12 доверие прокси включено по умолчанию **для всех** прокси: `ClientIP()` может взять адрес из `X-Forwarded-For`/`X-Real-IP`, если заголовок прислали. Сервис не вызывает `SetTrustedProxies`, поэтому:

- при прямом подключении без прокси клиент может подделать `X-Forwarded-For` и обойти лимит;
- за обратным прокси, наоборот, все клиенты могут выглядеть одним IP, если прокси не настроен;
- NAT и корпоративные сети дают общую квоту на многих пользователей.

Это известное ограничение текущей конфигурации. Перед публичным развёртыванием нужно явно настроить доверенные прокси (или отключить доверие) и/или ограничивать запросы на уровне прокси. В документации [api.md](api.md) это отмечено как ограничение.

## 6. Отказ кеша

Если `Increment` вернул ошибку (и fallback тоже не справился), лимитер пишет предупреждение и **пропускает** запрос: доступность входа важнее строгости лимита. Поэтому при сломанном Redis возможен временный обход лимитов — это осознанный fail-open.

При настроенном fallback ошибка Redis обычно не доходит до лимитера: счётчик уходит в память, предупреждение троттлится раз в минуту.

## 7. Ответ 429

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 37
Content-Type: application/json

{"error":{"code":"RATE_LIMITED","message":"Слишком много запросов. Попробуйте позже."}}
```

`Retry-After` — целое число секунд до следующего окна. Клиенту стоит подождать указанное время, а не повторять сразу.

## 8. Ограничения

- Только фиксированное окно; скользящего окна и token bucket нет.
- Только по IP; лимитов по пользователю, email или API-ключу нет.
- Нет белого списка и ручного сброса через API.
- Нет метрик и заголовков состояния лимита.
- `ClientIP()` без настроенных доверенных прокси — риск подмены IP (см. раздел 5).
- Лимиты не защищают от распределённого перебора с множества IP; для этого нужен внешний слой.
- В памяти без Redis лимит локальный для экземпляра.
