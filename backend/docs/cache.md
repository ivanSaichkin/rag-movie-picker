# Кеш каталога

Документ описывает кеш каталога RAG: что именно кешируется, как читается и обновляется, как ведёт себя при недоступном RAG и какие у него ограничения. Общий слой кеша (Redis, память, fallback) — в [caching.md](caching.md); HTTP-ручка каталога — в [api.md](api.md).

## 1. Зачем кешировать каталог

`GetCatalog` в RAG отдаёт жанры, границы годов, лимиты и доступные стратегии. Это дорогой вызов (обращение по gRPC к Python), а меняется каталог только вместе с индексом, то есть редко. Поэтому Go-сервис [catalog.Service](../internal/infrastructure/services/catalog/service.go) держит ответ в кеше 5 минут.

Карточки фильмов (`GetMovie`) не кешируются: они должны соответствовать текущему индексу, а один вызов дешёвый.

## 2. Путь запроса

```text
GET /api/v1/catalog
  → CatalogHandler.Catalog
    → catalog.Service.Catalog
      → cache.Get("catalog:current")
          найдено и JSON валиден → ответ из кеша
          промах/ошибка/битый JSON → RAG.GetCatalog
            → cache.Set("catalog:current", json, 5m)  (best effort)
            → ответ клиенту
```

`GET /api/v1/movies/{movie_id}` идёт мимо кеша: `catalog.Service.Movie` сразу вызывает `RAG.GetMovie`.

## 3. Ключ и значение

| Свойство | Значение |
|---|---|
| Ключ | `catalog:current` |
| TTL | 5 минут |
| Формат | JSON, отдельные `cached*`-структуры внутри сервиса |
| Область | Общая для всех пользователей; каталог не персонализирован |

Сериализованная форма:

```json
{
  "genres": [{"id": 28, "name": "Action"}],
  "movie_count": 4803,
  "year_from": 1902,
  "year_to": 2017,
  "default_results": 10,
  "max_results": 50,
  "available_strategies": ["bm25", "transformer", "hybrid"],
  "default_strategy": "hybrid"
}
```

`year_from` и `year_to` опускаются, если RAG их не сообщил. `max_candidates` из контракта RAG в кеш и в HTTP-ответ не попадает: бэкенд это поле пока не использует (см. раздел «Контракт RAG» в [backend/README.md](../README.md)).

Формат хранения намеренно не совпадает с доменной моделью и HTTP DTO: домен не знает про JSON-теги, а смена HTTP-контракта не требует переписывать кеш.

## 4. Чтение, запись и ошибки

`fromCache` трактует любую проблему как промах:

- ошибка кеша (`Redis` недоступен) → предупреждение в лог, запрос в RAG;
- ключа нет → запрос в RAG;
- JSON не декодируется → предупреждение, запрос в RAG и перезапись.

`toCache` не влияет на ответ: ошибка кодирования или записи только логируется. Клиент получает данные RAG независимо от судьбы кеша.

Если кеш пуст, а RAG недоступен, каталог отвечает 503 `DEPENDENCY_UNAVAILABLE`; при таймауте RAG — 504 `DEADLINE_EXCEEDED`. Если кеш заполнен, каталог продолжает отвечать при лежащем RAG — до истечения TTL.

## 5. Актуальность

- Изменения каталога в RAG становятся видны не позже чем через 5 минут (или сразу после `DEL catalog:current`).
- Отдельного API инвалидации нет: TTL — единственный штатный механизм.
- При нескольких экземплярах API с Redis кеш общий; с памятью — у каждого свой, поэтому TTL истекает независимо.
- Рестарт процесса с памятью очищает каталог; с Redis каталог переживает рестарт API, но не рестарт Redis (в Compose он без персистентности).
- Нет stale-while-revalidate и singleflight: на границе TTL несколько параллельных запросов могут одновременно сходить в RAG. Для каталога это допустимо, но при высокой нагрузке стоит помнить.

## 6. Влияние на подбор

`recommendation.Service` перед вызовом RAG берёт каталог через тот же кеш и валидирует по нему:

- `limit` против `max_results` (при отсутствии — 50);
- жанры, годы, рейтинг;
- `strategy` против `available_strategies`.

Значит, до 5 минут после изменения каталога сервис может отклонить новый жанр или стратегию, которых ещё нет в кеше, либо принять старые. RAG всё равно валидирует запрос повторно, поэтому расхождение не приводит к некорректной выдаче — только к лишнему 422/400 на устаревших данных. После истечения TTL ограничения обновляются.

## 7. Ограничения

- Нет метрик попаданий/промахов и времени жизни записи.
- Нет отрицательного кеширования: ошибки RAG не запоминаются.
- Нет сжатия и ограничения размера значения: каталог небольшой, но формат не защищён от роста.
- Нет версии ключа: при изменении формата старые записи считаются промахом и перезаписываются.
- `max_candidates` и диагностика RAG не кешируются и не отдаются.
- Кеш не учитывает пользователя и не годится для персонализированных данных.
