# Кеширование

Документ описывает общий слой кеша Go-сервиса: зачем он нужен, какие реализации существуют, как выбирается Redis, что происходит при его отказе и какие данные вообще не кешируются. Конкретно кеш каталога разобран в [cache.md](cache.md); лимиты — в [rate-limiting.md](rate-limiting.md).

## 1. Роль кеша

Кеш — не источник истины и не обязательная зависимость. У него два потребителя:

| Потребитель | Что хранит | Зачем |
|---|---|---|
| Каталог RAG | JSON каталога под ключом `catalog:current` | `GetCatalog` дорогой, а каталог меняется редко |
| Ограничитель частоты | счётчики окон | Не считать лимиты в памяти процесса, если экземпляров несколько |

Если кеш недоступен, сервис продолжает работать: каталог запрашивается у RAG, лимиты считаются в памяти или временно ослабляются. Это осознанный fail-open/fail-soft, а не скрытая ошибка.

## 2. Контракт

Интерфейс — [ports.Cache](../internal/domain/ports/services.go):

```go
type Cache interface {
    Get(ctx context.Context, key string) ([]byte, bool, error)
    Set(ctx context.Context, key string, value []byte, ttl time.Duration) error
    Increment(ctx context.Context, key string, ttl time.Duration) (int64, error)
    Delete(ctx context.Context, key string) error
}
```

`Get` различает промах и ошибку: `found=false, err=nil` — ключа нет, `err != nil` — слой сломан. Это позволяет каталогу трактовать сбой как промах, а лимитеру — как основание пропустить запрос.

## 3. Реализации

| Реализация | Файл | Поведение |
|---|---|---|
| `RedisCache` | [redis.go](../internal/infrastructure/adapters/cache/redis.go) | Сеть, TTL, атомарный `INCR` через Lua; соединение ленивое |
| `InMemoryCache` | [memory.go](../internal/infrastructure/adapters/cache/memory.go) | `map` под мьютексом, TTL, копирование значений, периодическая уборка |
| `FallbackCache` | [fallback.go](../internal/infrastructure/adapters/cache/fallback.go) | Пробует основной кеш, при ошибке идёт во вторичный; пишет предупреждение не чаще раза в минуту |

`RedisCache` не делает `Ping` при старте: сломанный Redis не должен мешать запуску. Таймауты `DialTimeout`, `ReadTimeout`, `WriteTimeout` берутся из `REDIS_TIMEOUT_SECONDS` (по умолчанию 1 секунда). `Increment` выполняет скрипт: `INCR` и `PEXPIRE` только при создании ключа, чтобы окно не продлевалось каждым запросом.

`InMemoryCache` хранит копии `[]byte`, поэтому вызывающий не может изменить данные после `Set`. Просроченные ключи удаляются лениво при чтении и пачкой каждые 1024 операции (`maybeSweep`), иначе поток уникальных ключей (IP-адреса) рос бы бесконечно.

`FallbackCache` не пытается «лечить» Redis и не кеширует ошибку: каждая операция снова идёт в основной кеш. Предупреждения троттлятся, потому что сломанный Redis иначе залил бы лог на каждом запросе.

## 4. Выбор реализации

Сборка — [buildCache](../internal/app/infrastructure.go):

```text
REDIS_ADDR пуст  → InMemoryCache
REDIS_ADDR задан → FallbackCache(RedisCache, InMemoryCache)
```

При старте в лог пишется `cache: in-memory` или `cache: redis with in-memory fallback`. Закрытие Redis выполняет точка сборки при остановке процесса.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `REDIS_ADDR` | пусто | Адрес Redis; пусто — память |
| `REDIS_PASSWORD` | пусто | Пароль |
| `REDIS_DB` | 0 | База 0–15 |
| `REDIS_TIMEOUT_SECONDS` | 1 | Таймаут операций, 1–60 |

В Compose Redis запускается без персистентности (`--save "" --appendonly no`): после рестарта счётчики и каталог теряются, но это допустимо, потому что кеш не является источником истины.

## 5. Ключи и TTL

| Ключ | TTL | Значение |
|---|---|---|
| `catalog:current` | 5 минут | JSON каталога, см. [cache.md](cache.md) |
| `ratelimit:login:<ip>:<unix>` | 1 минута | счётчик входов |
| `ratelimit:register:<ip>:<unix>` | 1 час | счётчик регистраций |
| `ratelimit:refresh:<ip>:<unix>` | 1 минута | счётчик refresh |

Префикс `ratelimit:` и временное окно в ключе делают окна фиксированными: новый ключ появляется на границе окна, старый истекает сам. Формат и расчёт `Retry-After` описаны в [rate-limiting.md](rate-limiting.md).

## 6. Поведение при сбоях

| Сбой | Каталог | Лимиты |
|---|---|---|
| Redis недоступен, настроен fallback | Чтение/запись уходят в память; каталог может быть запрошен у RAG повторно | Счётчики уходят в память; на нескольких экземплярах лимиты становятся независимыми |
| Redis недоступен, fallback нет (память) | Работает память | Работает память |
| Кеш вернул ошибку | Промах, запрос в RAG | Запрос пропускается (fail-open) |
| В кеше повреждённый JSON каталога | Промах, запрос в RAG, перезапись | Не применимо |

Сбой кеша не превращается в 5xx для клиента. Исключение — если после промаха недоступен сам RAG: тогда каталог/подбор отвечают 503, но это ошибка зависимости, а не кеша.

После восстановления Redis трафик снова идёт в него; память не синхронизируется. Поэтому возможны «прыжки» лимитов и повторные `GetCatalog` сразу после восстановления — это принятая цена простоты.

## 7. Что не кешируется

- Карточки фильмов (`GetMovie`): должны не отставать от индекса, один вызов дешёвый.
- История и личные списки: читаются из PostgreSQL, кеш не нужен и усложнил бы консистентность.
- Access/refresh-токены, сессии, пароли: только PostgreSQL и cookie.
- Результаты подбора: каждый запрос сохраняется в историю, кешировать его нельзя без изменения семантики.
- Ответы `/health` и `/ready`: проверяются на каждом запросе.

## 8. Ограничения

- Нет метрик попаданий/промахов и размера кеша; только логи предупреждений.
- Нет ограничения числа ключей в памяти: уборка снижает риск, но при большом числе IP карта может вырасти.
- Нет singleflight и stale-while-revalidate: истечение `catalog:current` может вызвать несколько параллельных `GetCatalog` в нескольких экземплярах.
- Ключи не версионируются: формат значения меняется вместе с кодом и только через новую версию приложения; старые записи считаются промахом по ошибке декодирования.
- Инвалидации через API нет; каталог обновляется по TTL, вручную — `DEL catalog:current`.
- Память процесса не разделяется между экземплярами; общие лимиты и каталог требуют Redis.
