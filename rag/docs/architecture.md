# Устройство RAG сервиса

Python-сервис подбирает фильмы из TMDB 5000 Movie Dataset по текстовому запросу и фильтрам. Сначала поиск находит кандидатов, затем LLM выбирает фильмы из этого списка и объясняет выбор. Это retrieval-augmented generation — генерация на основе найденных данных.

Здесь описана текущая реализация. Установка, импорт, запуск и команды проверок находятся в [README сервиса](../README.md). Общая архитектура приложения — в [README проекта](../../README.md).

## Границы ответственности

RAG принимает запрос по gRPC и возвращает рекомендации. Он отвечает за импорт каталога, векторы, поиск, фильтры и обращение к LLM.

Авторизация, история поиска, «Хочу посмотреть» и оценки относятся к отдельному Go-бэкенду и его PostgreSQL. RAG не получает пользовательские пароли или сессии, не хранит историю и не использует оценки для персонализации. Подключение Go-бэкенда и сайта к RAG — отдельная часть проекта.

Есть два независимых сценария:

```text
Подготовка каталога
CSV → MovieFormatter → BM25 + трансформер → Qdrant
                    → статистика и manifest на диске

Обработка запроса
Go → gRPC → RagService
              ├─ LLM: подготовка английского запроса
              ├─ RetrievalPipeline
              │    ├─ BM25 → Qdrant
              │    ├─ трансформер → Qdrant
              │    └─ RRF → кандидаты
              └─ LLM: выбор и объяснения → проверка → ответ Go
```

Ветки поиска в текущем коде выполняются последовательно. Схема показывает разделение ответственности, а не параллельное выполнение.

## Данные и Qdrant

Один фильм — один поисковый документ и одна точка Qdrant. Разбиения на чанки нет.

Текст для поиска состоит из названия, оригинального названия, описания `overview`, жанров и ключевых слов. Одинаковые названия не повторяются. Год и рейтинг используются как фильтры, а не добавляются в поисковый текст.

Коллекция по умолчанию называется `movies_v1`. После импорта каждая точка содержит:

| Поле | Содержимое |
| --- | --- |
| ID точки | `movie_id` из TMDB |
| Вектор `bm25` | Разреженные координаты `indices` и `values` |
| Вектор `semantic` | Плотный нормализованный вектор, расстояние Cosine |
| Payload карточки | `movie_id`, `title`, `original_title`, `overview`, `genres`, `keywords`, `year`, `rating`, `vote_count` |
| Служебный payload | `genre_ids` для фильтрации и `index_id` для проверки версии |

В Qdrant не записываются ответы LLM, запросы пользователя или история. Длительность и язык фильма сейчас также не импортируются.

Рядом с сервисом хранится `INDEX_STATE_DIR/manifest.json`: словарь и статистика BM25, SHA-256 исходного CSV, параметры индекса, revision модели, размерность, предел длины текста, каталог жанров, число фильмов и статус готовности. Для восстановления сервиса нужны **и Qdrant, и соответствующий manifest**.

## Импорт каталога

Команда `movie-rag import` выполняет следующие действия:

1. Читает CSV и разбирает JSON-поля без `eval`. Некорректные строки пропускаются с записью номера строки в лог; конфликтующие записи с одинаковым ID останавливают импорт.
2. Формирует поисковый текст каждого фильма и рассчитывает статистику BM25 по всему принятому корпусу.
3. Создаёт новую коллекцию с двумя именованными векторами. Для `genre_ids`, `year`, `rating`, `index_id` запрашиваются payload-индексы.
4. Сохраняет manifest со статусом `building`.
5. Пакетно рассчитывает оба вектора и записывает фильмы в Qdrant.
6. Проверяет схему коллекции, количество точек и их `index_id`, затем атомарно сохраняет manifest со статусом `ready`.

Отсутствующий год остаётся неизвестным. Рейтинг без голосов считается неизвестным, а не нулевым. Внешний LLM при импорте не вызывается.

Повторный импорт с прежним CSV и настройками проверяет существующий индекс без повторной записи. Изменение корпуса, модели, форматтера или параметров BM25 требует новой коллекции и новой директории состояния. Незавершённый импорт автоматически не продолжается; существующая коллекция не удаляется.

Импорт и сервер удерживают один файловый lock в директории состояния. Они не могут одновременно работать с одной такой директорией. Это локальная блокировка, не защита общей коллекции от процессов на разных хостах.

## Два типа поиска

### Разреженный BM25

BM25 реализован в коде без готовой поисковой библиотеки. Текст приводится к нижнему регистру, токены выделяются выражением `[a-z0-9]+`, без стемминга. Словарь отсортирован, поэтому координаты воспроизводимы.

При импорте рассчитываются число документов `N`, средняя длина `avgdl` и число документов с каждым словом `df(t)`. Параметры по умолчанию: `k1 = 1.5`, `b = 0.75`.

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))

weight(t, d) = tf(t, d) × (k1 + 1)
               / (tf(t, d) + k1 × (1 - b + b × |d| / avgdl))

BM25(q, d) = Σ idf(t) × weight(t, d)
```

Сумма берётся по уникальным известным словам запроса. Документный вектор хранит `weight`, вектор запроса — `idf`; Qdrant получает BM25-score через их скалярное произведение. Автоматический IDF Qdrant выключен, чтобы не учитывать его дважды.

Неизвестные слова игнорируются. Пустой sparse-вектор и нулевые оценки не дают результатов. Фильтры не пересчитывают статистику корпуса.

### Плотные трансформерные векторы

Используется `intfloat/multilingual-e5-small` через Sentence Transformers, с revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`. Модель запускается локально, по умолчанию на CPU, и не дообучается на каталоге.

Адаптер добавляет `passage: ` к документам и `query: ` к запросам, затем нормализует векторы. Размерность и максимальная длина читаются из модели; размерность проверяется против коллекции. Длинные документы обрезаются по пределу модели, количество таких документов сохраняется при импорте.

Мультиязычный эмбеддер получает исходный русский запрос и сопоставляет его с английскими описаниями. Это отдельная модель от LLM: эмбеддер выдаёт числовой вектор, LLM — текстовый JSON-ответ.

### Объединение RRF

Настройка `RETRIEVAL_STRATEGY` задаёт `sparse`, `dense` или `hybrid`. В индексе при любой стратегии хранятся оба вектора.

В hybrid результаты объединяются в Python через Reciprocal Rank Fusion:

```text
RRF(movie) = Σ 1 / (60 + место фильма в списке ветки)
```

Места начинаются с 1. Отсутствие фильма в списке даёт нулевой вклад; повторы объединяются по ID. При равенстве итоговой оценки порядок определяется `movie_id`. Число 60 настраивается через `RRF_K` и не связано с количеством рекомендаций.

Например, за места 2 и 5 фильм получит `1/62 + 1/65 ≈ 0.03151`. Фильм только на первом месте одной ветки получит `1/61 ≈ 0.01639`. Так согласие двух поисков может поднять фильм выше.

RRF использует позиции, а не складывает несопоставимые BM25-score и cosine. Это способ объединения рейтингов, а не вероятность того, что фильм понравится.

## Как обрабатывается запрос на 10 фильмов

Пример входных полей gRPC в условной JSON-записи, не HTTP-запрос:

```json
{
  "query": "Напряжённая фантастика про космос",
  "limit": 10,
  "filters": {
    "genre_ids": [878],
    "year_from": 2000,
    "year_to": 2020,
    "min_rating": 7
  }
}
```

1. **Проверка.** Обработчик удаляет пробелы по краям текста, проверяет длину, лимит и диапазоны. Сервис проверяет жанры и готовность индекса.
2. **Подготовка BM25.** В sparse/hybrid LLM готовит английский поисковый запрос. Эта стадия вызывается и для уже английского входа. Dense-поиск получает исходный текст.
3. **Поиск с запасом.** Каждая ветка возвращает до `K = min(число фильмов, max(30, 3 × limit))` кандидатов. Для 10 рекомендаций это до 30 фильмов от каждой ветки.
4. **Фильтрация.** Одинаковые ограничения применяются внутри обоих запросов Qdrant до top-K. Несколько жанров означают «любой из выбранных»; разные виды фильтров объединяются через «И». Границы включены, неизвестный год или рейтинг не проходит соответствующий фильтр.
5. **Объединение.** RRF объединяет два списка, после чего остаётся до 30 кандидатов. Если кандидатов нет, возвращается `empty` без финального вызова LLM.
6. **Выбор.** LLM получает исходный запрос, фильтры, требуемое количество и карточки кандидатов. Если контекст слишком большой, кандидаты удаляются с конца рейтинга.
7. **Валидация.** Ответ должен содержать не более 10 уникальных ID из переданного списка и непустые объяснения. Карточки берутся из результатов поиска, а не из ответа модели. Порядок успешной подборки задаёт LLM.
8. **Ответ.** Возвращаются фильмы, объяснения, режим работы, фактически использованная стратегия и предупреждения.

Фильтры автоматически не ослабляются. Результатов может быть меньше 10: подходящих кандидатов мало, контекст сокращён или LLM отклонила часть фильмов.

## Работа с LLM

`OpenRouterClient` обращается к `/chat/completions`, запрашивает JSON и использует `LLM_MODEL`. Модель генерации не задана по умолчанию: нужны ключ и выбранный идентификатор.

В обычном успешном hybrid-запросе есть два логических обращения: подготовка английского запроса и выбор фильмов. В dense — только выбор. При временных ошибках допускается один повтор каждого обращения в пределах оставшегося бюджета времени.

Внешнему провайдеру передаются пользовательский текст, а на стадии выбора — также фильтры и карточки кандидатов. Весь CSV и векторы не отправляются. Пользовательский текст и описания рассматриваются как данные, а не инструкции.

Код проверяет схему ответа, количество, уникальность и принадлежность ID кандидатам. Эта проверка не доказывает фактическую корректность объяснений: качество и обоснованность текста требуют отдельной оценки.

## gRPC и режимы ответа

Источник контракта — [rag.proto](../../proto/rag/v1/rag.proto). Python- и Go-клиенты генерируются из него.

| RPC | Назначение |
| --- | --- |
| `Recommend` | Принять `query`, `filters`, необязательный `limit`; вернуть `mode`, `strategy_used`, `items`, `warnings` |
| `GetMovie` | Получить карточку по положительному `movie_id` |
| `GetCatalog` | Получить жанры, число фильмов, диапазон лет и лимиты выдачи |
| Health `Check` | Проверить доступность и согласованность индекса |

Элемент `items` содержит `movie` и необязательный `reason`. Карточка включает `movie_id`, `title`, `year`, `genres`, `rating`, `vote_count`, `overview`. Неизвестные год и рейтинг, а также отсутствующее объяснение не устанавливаются в protobuf.

Текст запроса — от 1 до 1000 символов после trim. Если `limit` отсутствует, используется `DEFAULT_RESULTS=10`; явный 0 недопустим. По умолчанию `MAX_RESULTS=50`. Годы — от 1 до 9999, рейтинг — от 0 до 10.

| Ситуация | Поведение |
| --- | --- |
| LLM успешно выбрала фильмы | `mode=generated`, объяснения присутствуют |
| Нет кандидатов или LLM вернула допустимый пустой список | `mode=empty`, `NO_MATCHES` |
| Финальная генерация недоступна или ответ некорректен | `mode=retrieval_only`, поисковый top без объяснений, `GENERATION_UNAVAILABLE` |
| В hybrid не подготовлен английский запрос или отказала одна ветка | Оставшаяся ветка и `RETRIEVAL_DEGRADED` |
| Отказали все запрошенные ветки | gRPC `UNAVAILABLE`, не пустая успешная выдача |
| Индекс несовместим или не готов | Отказ запуска либо `UNAVAILABLE`, без маскировки через fallback |
| Сокращён контекст | `CONTEXT_LIMIT`; выбор по оставшимся кандидатам |
| Истёк бюджет или запрос отменён | `DEADLINE_EXCEEDED` или `CANCELLED`, без fallback |

`strategy_used` показывает `sparse`, `dense` или `hybrid`. Успешная, но пустая ветка не считается отказавшей. После финального выбора или fallback при недоборе добавляется `FEWER_RESULTS`; при раннем выходе из-за отсутствия кандидатов возвращается `NO_MATCHES`.

В sparse-only ошибка подготовки английского запроса возвращается как `UNAVAILABLE`. Без настроенной LLM hybrid может продолжить dense-поиск, но выдача будет без объяснений.

## Настройки и эксплуатационные ограничения

Настройки читаются из переменных окружения и `.env` в рабочей директории. Актуальные значения определены в [config.py](../src/movie_rag/config.py), пример — [.env.example](../.env.example).

| Настройка | Значение по умолчанию |
| --- | --- |
| `GRPC_ADDR`, `GRPC_WORKERS` | `127.0.0.1:50051`, 4 |
| `REQUEST_TIMEOUT_SECONDS` | 60 секунд |
| `QDRANT_URL`, `QDRANT_COLLECTION` | `http://127.0.0.1:6333`, `movies_v1` |
| `INDEX_STATE_DIR` | `.state` |
| `EMBEDDING_DEVICE`, `EMBEDDING_BATCH_SIZE` | `cpu`, 16 |
| `RETRIEVAL_STRATEGY`, `RRF_K` | `hybrid`, 60 |
| `LLM_TIMEOUT_SECONDS` | 20 секунд |
| `LLM_CONTEXT_BYTES`, `LLM_MAX_OUTPUT_TOKENS` | 24000 байт UTF-8, 4096 выходных токенов |

`QDRANT_PATH` переключает сервис на embedded Qdrant. В этом режиме фильтры работают, но payload-индексы не ускоряют поиск. Для отдельного сервера используется `QDRANT_URL`.

Обработчики синхронные, с ограничением числа одновременных RPC. Эмбеддер загружается один раз, вычисления сериализованы блокировкой. В sparse-only сервер не загружает трансформер, но импорт всё равно строит оба типа векторов.

Для `Recommend` действует меньший из клиентского дедлайна и серверного бюджета. Отмена проверяется между этапами; запущенный inference PyTorch нельзя принудительно остановить. Проверки готовности и чтение карточек не используют сквозной `Budget`, а зависят от таймаутов клиента хранилища.

`LLM_CONTEXT_BYTES` учитывает размер подготовленного текста в UTF-8, а не точное число токенов провайдера. Его необходимо согласовать с моделью. Поисковый fallback не имеет гарантии релевантности: dense-поиск может найти соседей даже для неподходящего запроса.

gRPC работает без TLS и собственной авторизации, поэтому порт предназначен для localhost или доверенной внутренней сети. Реализован health `Check`, но не `Watch`; стриминга рекомендаций нет. Логи обработчика содержат `request_id`, код и длительность, не полный запрос или секреты.

## Проверка качества

Тесты покрывают ручной расчёт BM25 и RRF, фильтры Qdrant, импорт и manifest, ответы LLM, fallback и gRPC-контракт. В интеграционных тестах используются embedded Qdrant и локальный gRPC, в тестах LLM — подставной клиент. Отдельно включается smoke-test кешированной трансформерной модели.

Для оценки рекомендаций нужен размеченный набор запросов и сравнение `sparse`, `dense`, `hybrid` и итоговой выдачи LLM. Основные показатели: Precision@k, соблюдение фильтров, недобор, обоснованность объяснений, задержка и доля fallback. Прохождение функциональных тестов не заменяет эту оценку.
