# Оценка рекомендера

Бенчмарк обращается к работающему Python-сервису по gRPC. Он не запускает сервис и не перестраивает индекс. Нужны Python 3.12–3.13 и uv; Qdrant и модели клиенту оценки не нужны.

## Корпус и эталон

Используется полный каталог из 4 799 пригодных записей TMDB. Русские описания подготовлены из обогащения; при отсутствии перевода остаётся исходный текст. Путь берётся из `index.dataset_path` в `../recommender/config.toml`. Подготовка и индексация описаны в [README рекомендера](../recommender/README.md).

[Golden set](goldenset/queries.jsonl) содержит **10 обычных русских запросов, 121 оценку релевантности и 5 ловушек**. Обычные темы: космос, ограбления, время, семейная анимация, расследования, искусственный интеллект, суд, Вторая мировая война, бокс, выживание. На каждый запрос размечены 10–16 фильмов; минимум 3 имеют оценку ≥2.

Ловушки проверяют три отсутствующих точных названия и два диапазона лет без фильмов. Это проверка контракта отказа приложения, а не доказательство способности LLM отвергать любые некорректные запросы. Для более широкой проверки добавляйте неизвестные сведения, противоречивые пожелания и перефразировки; не подгоняйте реализацию под конкретные названия.

**Отличие от задания:** в PDF указан корпус из 30 документов. Здесь сохранён полный каталог по договорённости; уменьшенный учебный корпус не создан. Использование 4 799 документов вместо 30 нужно согласовать с преподавателем. Также собственные веса BM25 ищутся через Qdrant — допустимость этого вместо отдельного самописного инвертированного индекса зависит от методички.

## Запуск

Сначала запустите Qdrant и рекомендатель с русским `config.toml`. Далее из `evaluation`:

```powershell
uv sync --locked --group dev
uv run benchmark.py --mode validate

# Три стратегии, 10 обычных запросов + 5 ловушек на каждую. LLM полностью выключена.
uv run benchmark.py --mode quality --k 10 --disable-llm --output-dir ../../research/results

# Тот же набор и K с финальным отбором LLM. Ключ хранится только у сервера.
uv run benchmark.py --mode quality --k 10 --generate-explanations --output-dir ../../research/results

# Сохранить также промпты, сырые ответы, usage и серверные тайминги.
uv run benchmark.py --mode quality --k 10 --generate-explanations --inspect --output-dir ../../research/results

# Ограниченная нагрузка без LLM.
uv run benchmark.py --mode load --k 10 --requests 30 --concurrency 1 2 4 --disable-llm --output-dir ../../research/results
```

Для второго прогона серверу нужны `llm.enabled=true`, модель и ключ в локальном `.env`. В русском конфиге `bm25.query_preparation="none"`, поэтому сравнение изолирует финальный отбор. Флаг `--generate-explanations` не включает LLM, отключённую на сервере. Нагрузочный прогон с LLM требует отдельного `--allow-llm-load` и может расходовать средства API.

Дополнительно доступны `--strategies bm25`, `--config`, `--address`, `--dataset`, `--goldenset`, `--repeats`, `--warmup`, `--timeout`, `--seed`. Смена `--dataset` меняет лишь локальную проверку, не индекс. Полный список — `uv run benchmark.py --help`.

## Метрики

| Метрика | Что оценивает |
| --- | --- |
| NDCG@K | Порядок с градациями релевантности, gain = 2^grade−1 |
| MAP@K | Среднее AP; релевантны grade ≥2; знаменатель AP = min(R,K) |
| Recall@K, MRR@K, Precision@K, Hit Rate@K | Полнота известных оценок, первая релевантная позиция, точность и наличие попадания |
| Correct Rejection Rate | Доля корректных отказов по контракту: пустая выдача либо явно помеченные альтернативы (`has_matches=false`) с пояснением |
| Accuracy полного ответа | Доля полностью правильных обычных ответов после ручной проверки |
| Время и нагрузка | Среднее, p50/p95/p99, RPS, ошибки, фактическая стратегия и режим |

**Метрики ранжирования считают только обычные запросы.** Ловушки исключены из их среднего. Ошибка обычного RPC даёт нулевые метрики; ошибка RPC или `GENERATION_UNAVAILABLE` на ловушке не считается корректным отказом. Альтернативы допустимы только с `has_matches=false`, непустым пояснением и `NO_RELEVANT_MATCHES`; проверяются ID, фильтры, дубликаты и лимит. Это автоматическая проверка структуры отказа, содержание пояснения следует дополнительно проверить вручную. Неоценённые фильмы, дубликаты, неизвестные ID и нарушения фильтров получают нулевой gain. Одинаковая оценка допускает любой взаимный порядок фильмов.

Полный правильный ответ соблюдает фильтры, содержит подходящие фильмы, не дублирует их и не приписывает им отсутствующие в каталоге факты. Поэтому Accuracy нельзя заменить точным совпадением порядка или NDCG. Разметка неполная: подходящий неоценённый фильм проверяется человеком по каталогу, а не автоматически объявляется выдумкой.

## Результаты и ручная проверка

Каждый запуск создаёт `run_N` в `--output-dir` (по умолчанию `evaluation/results`). Предыдущие запуски сохраняются.

- `metadata.json` — аргументы, хеши CSV и разметки, безопасные настройки, manifest, версии и Git-состояние.
- `goldenset.jsonl` — снимок разметки.
- `requests.jsonl` — запрос, ответ с описаниями, общим `explanation` и `has_matches`, режим, предупреждения, время, метрики и ожидаемое поведение.
- `summary.json`, `summary.csv` — агрегаты по стратегии, этапу и параллельности, включая CRR.
- `warmup.jsonl` — прогрев, исключённый из измерений.
- При `--inspect` каждый ответ дополнительно содержит `diagnostics`: кандидатов, промпты, HTTP-попытки с `usage` и серверные тайминги. Используется `InspectRecommendation`; ключи редактирует сервер. Диагностика увеличивает ответ и время сериализации, поэтому флаг запрещён для нагрузочных прогонов. Расход прогрева находится отдельно в `warmup.jsonl`; неизвестный расход не следует считать нулевым.
- `answer_review.jsonl` — шаблон ручной проверки обычных quality-ответов.

В `answer_review.jsonl` заполните `answer_correct` значением `true` или `false`, при необходимости `comment`. Сопоставляйте ответ из `requests.jsonl` по `query_id`, стратегии и `sequence`. Затем:

```powershell
uv run grade_answers.py ../../research/results/run_N
```

Появится `answer_accuracy.json`. Пока остаются непроверенные успешные ответы, Accuracy равна `null`; RPC-ошибки учитываются как неправильные ответы. Повторный бенчмарк создаёт новый каталог, поэтому ручная разметка предыдущего запуска не стирается.

Конфиг фиксируется по разрешённым полям, ключ API не сохраняется. Локальный снимок настроек не удостоверяет конфигурацию запущенного сервера. Нагрузка использует ограниченное число клиентских потоков; это не определение максимальной мощности системы. p95/p99 на малом числе запросов нестабильны.

Оценки — черновые, покрытие релевантных фильмов неполное. Перед финальным сравнением нужна ручная проверка и отдельный набор, на котором не подбирались параметры. [Исторические результаты на английском корпусе](../docs/evaluation/llm-comparison.md) нельзя напрямую сравнивать с новым русским набором.

```powershell
uv run ruff check .

uv run python -m unittest discover -s tests -v
```

Тесты используют синтетический CSV и локальный gRPC-сервер; платные API не вызываются.
