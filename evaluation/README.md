# Оценка рекомендаций

CLI для проверки качества и задержек RAG через gRPC. Только стандартная библиотека Python, `grpcio` и `protobuf`; Jupyter, Qdrant и модели клиенту не нужны. Python 3.12–3.13, менеджер окружения uv.

## Подготовка

Команды ниже выполняются из `evaluation`:

```powershell
uv sync --locked --group dev
uv run benchmark.py --mode validate
```

TMDB CSV не включён в репозиторий. Путь берётся из `index.dataset_path` выбранного `../rag/config.toml`, относительно самого TOML. По умолчанию ожидается соседний с репозиторием каталог `../data/raw/TMDB 5000 Movie Dataset/tmdb_5000_movies.csv`. Для другого расположения передайте `--dataset "полный/путь/tmdb_5000_movies.csv"`; это меняет только клиентский файл проверки, а не индекс сервера.

Golden set: [goldenset/queries.jsonl](goldenset/queries.jsonl), 6 английских запросов и 78 черновых оценок. `query_ru` поясняет намерение; в gRPC отправляется `query`. Список неполный, требует ручной проверки и расширения. Не меняйте оценки под полученную выдачу и не используйте этот же набор как независимый тест после подбора параметров.

Для измерений запустите RAG отдельно с соответствующим TOML, импортируйте тот же CSV и подготовьте Qdrant. Benchmark не запускает сервер, не перестраивает индекс и не переключает серверные настройки. Локальный снимок TOML не подтверждает настройки уже работающего процесса.

## Запуск

```powershell
# Качество: каждый запрос по одному разу для каждой доступной стратегии.
uv run benchmark.py --mode quality --k 10

# Короткий прогон качества и нагрузки: 126 запросов + 3 прогрева для трёх стратегий.
uv run benchmark.py --mode all --k 10 --requests 12 --concurrency 1 2 4 --warmup 1 --repeats 1 --timeout 60 --seed 42

# Тот же сценарий с финальным выбором LLM.
uv run benchmark.py --mode all --k 10 --requests 12 --concurrency 1 2 4 --warmup 1 --repeats 1 --timeout 60 --seed 42 --generate-explanations --allow-llm-load
```

Для прогона без LLM на сервере задайте `llm.enabled=false`, `bm25.query_preparation="none"`. Для прогона с LLM настройте `llm.enabled=true`, модель и API-ключ в окружении серверного процесса, затем перезапустите RAG. В версии с загрузкой `.env` ключ можно передать через этот файл; клиент оценки ключ не читает. BM25-подготовка регулируется отдельно: для изолированной оценки финального выбора оставьте `query_preparation="none"` в обоих прогонах. При `query_preparation="llm"` сравнивается весь конвейер, включая подготовку запроса.

`--generate-explanations` запрашивает финальный выбор, но не включает отключённый на сервере LLM. Пул кандидатов задаётся серверными `search.min_candidates` и `candidate_multiplier`; при K=10 и настройках по умолчанию это до 30 фильмов до ограничения контекста. `--allow-llm-load` явно разрешает нагрузку при включённой LLM: прогон может расходовать средства API. Один флаг генерации не отключает перевод BM25.

Другие параметры (`uv run benchmark.py --help`):

| Параметр | Назначение |
| --- | --- |
| `--config`, `--address` | TOML для снимка настроек и адрес gRPC; не меняют работающий сервер |
| `--dataset`, `--goldenset` | Другой CSV или JSONL разметки |
| `--strategies bm25 transformer hybrid` | Подмножество доступных стратегий |
| `--k`, `--repeats` | Размер выдачи и повторы quality-этапа |
| `--requests`, `--concurrency` | Число запросов **на каждый** нагрузочный этап и число клиентских потоков |
| `--warmup`, `--seed`, `--timeout` | Прогрев на стратегию, порядок запросов и дедлайн RPC в секундах |
| `--output-dir` | Каталог результатов; по умолчанию `evaluation/results` |

## Метрики и результаты

- NDCG@K: gain `2^grade-1`, discount `log2(rank+1)`.
- MAP@K: среднее AP@K; релевантны оценки ≥2, знаменатель AP — `min(R,K)`, где R — число известных релевантных фильмов.
- Precision@K, Recall@K по известной разметке, MRR@K и hit rate@K.
- Средняя задержка и p50/p95/p99, успешные RPS, ошибки RPC, предупреждения, режимы и фактическая стратегия, недобор и покрытие каталога.

Неоценённые фильмы, неизвестные ID, нарушения фильтров и повторные ID получают нулевой gain; дубликаты занимают место. Ошибки RPC дают нулевые метрики и остаются в среднем. Fallback `retrieval_only` оценивается по фактической выдаче и учитывается в `mode_counts`; статус `completed` сам по себе не означает успех генерации для всех запросов.

Нагрузка — closed-loop клиент с ограниченными потоками, не тест максимальной мощности. Задержка измеряется вокруг RPC после прогрева, включает серверные очереди и LLM, но исключает очередь клиентского executor. RPS считается по полному времени этапа. p95/p99 на 12 запросах нестабильны.

Каждый запуск создаёт новый `results/run_N`, не перезаписывая предыдущий:

| Файл | Содержимое |
| --- | --- |
| `metadata.json` | Аргументы, хеши CSV/разметки/конфига, безопасный снимок конфигурации и локального manifest, версии клиента, Git и каталог сервера |
| `goldenset.jsonl` | Использованная разметка |
| `requests.jsonl` | Запросы, ответы, время, предупреждения и метрики по каждому измерению |
| `warmup.jsonl` | Отдельные ответы прогрева |
| `summary.json`, `summary.csv` | Агрегаты отдельно по стратегии, этапу и параллельности |

Секреты из окружения не сохраняются; TOML фиксируется по списку разрешённых полей. Результаты содержат тексты запросов и объяснений, игнорируются Git. Историческое сравнение — в [отчёте](../docs/evaluation/llm-comparison.md).

## Тесты

```powershell
uv run ruff check .
uv run ruff format --check .
uv run python -m unittest discover -s tests -v
```

Тесты используют синтетический CSV и временный локальный gRPC-сервер; не требуют TMDB, Qdrant, модели или ключа API. Реальные ID и названия проверяйте отдельно через `--mode validate` на исходном CSV.
